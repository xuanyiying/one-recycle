# 消息中间件集成需求文档

## 介绍

为了提高OneRecycle系统的高可用性、可扩展性和容错能力，需要引入消息中间件来解耦微服务之间的同步调用，实现异步处理和事件驱动架构。本文档定义了消息中间件集成的需求和验收标准。

## 背景

当前系统存在以下高可用性问题：
1. 微服务间通过gRPC直接同步调用，服务故障会导致级联失败
2. 订单处理、通知发送等关键业务流程缺乏异步处理机制
3. 缺乏任务重试和失败恢复机制
4. 跨服务事务一致性难以保证
5. 系统扩展性受限于服务间的强耦合

## 需求

### Requirement 1: 技术选型与架构设计

**User Story:** 作为系统架构师，我需要选择合适的消息中间件技术方案，以便为系统提供可靠的异步消息处理能力。

#### Acceptance Criteria

1. WHEN 进行技术选型时 THEN 系统应评估至少3种主流消息中间件方案（RabbitMQ、Kafka、Redis+Bull）
2. WHEN 评估技术方案时 THEN 应考虑以下因素：部署复杂度、学习曲线、性能、可靠性、与现有技术栈的兼容性
3. WHEN 完成技术选型时 THEN 应输出详细的技术选型文档，包含对比分析和选型理由
4. WHEN 设计架构时 THEN 应定义清晰的消息队列命名规范和事件类型
5. WHEN 设计架构时 THEN 应包含消息重试策略、死信队列处理和监控方案

### Requirement 2: 消息队列服务开发

**User Story:** 作为后端开发者，我需要开发独立的消息队列服务，以便统一管理所有异步任务和事件处理。

#### Acceptance Criteria

1. WHEN 创建消息队列服务时 THEN 应创建独立的message-queue-service微服务
2. WHEN 配置消息队列时 THEN 应支持通过环境变量配置Redis连接参数
3. WHEN 定义队列时 THEN 应至少包含以下队列：订单队列、通知队列、支付队列、派单队列
4. WHEN 处理消息时 THEN 应实现消息生产者服务（Producer Services）
5. WHEN 处理消息时 THEN 应实现消息消费者处理器（Consumer Processors）
6. WHEN 消息处理失败时 THEN 应支持自动重试机制（指数退避策略）
7. WHEN 消息多次失败时 THEN 应将消息移入死信队列（DLQ）

### Requirement 3: 订单流程异步化改造

**User Story:** 作为产品经理，我希望订单创建和处理流程异步化，以便提高系统响应速度和用户体验。

#### Acceptance Criteria

1. WHEN 用户创建订单时 THEN 订单服务应立即返回成功响应，并将订单处理任务加入队列
2. WHEN 订单创建成功时 THEN 应发布"订单创建"事件到消息队列
3. WHEN 处理订单创建事件时 THEN 应触发以下异步任务：库存检查、价格计算、通知发送
4. WHEN 订单状态变更时 THEN 应发布"订单状态变更"事件
5. WHEN 订单需要派单时 THEN 应将派单任务加入延迟队列（延迟5分钟执行）
6. WHEN 订单被取消时 THEN 应发布"订单取消"事件并触发退款流程

### Requirement 4: 通知服务异步化改造

**User Story:** 作为运营人员，我希望所有通知（短信、推送、邮件）都通过消息队列异步发送，以便提高系统稳定性。

#### Acceptance Criteria

1. WHEN 需要发送通知时 THEN 应将通知任务加入通知队列而非同步发送
2. WHEN 处理通知任务时 THEN 应支持多种通知类型：短信、推送通知、邮件
3. WHEN 通知发送失败时 THEN 应自动重试最多3次
4. WHEN 通知多次失败时 THEN 应记录失败日志并告警
5. WHEN 发送批量通知时 THEN 应支持批量处理以提高效率
6. WHEN 通知有优先级时 THEN 应支持优先级队列（高优先级通知优先处理）

### Requirement 5: 支付回调异步处理

**User Story:** 作为支付系统开发者，我需要异步处理支付回调，以便确保支付结果可靠处理并避免阻塞第三方支付平台。

#### Acceptance Criteria

1. WHEN 收到支付回调时 THEN 应立即返回成功响应给支付平台
2. WHEN 收到支付回调时 THEN 应将回调数据加入支付队列进行异步处理
3. WHEN 处理支付回调时 THEN 应验证签名和幂等性
4. WHEN 支付成功时 THEN 应更新订单状态并发布"支付成功"事件
5. WHEN 支付失败时 THEN 应更新订单状态并发布"支付失败"事件
6. WHEN 处理支付事件时 THEN 应触发后续业务流程（如发货、通知等）

### Requirement 6: 监控和管理界面

**User Story:** 作为系统管理员，我需要监控消息队列的运行状态，以便及时发现和处理问题。

#### Acceptance Criteria

1. WHEN 访问监控界面时 THEN 应显示所有队列的实时状态（等待、处理中、已完成、失败）
2. WHEN 查看队列详情时 THEN 应显示队列中的任务列表和详细信息
3. WHEN 任务失败时 THEN 应支持手动重试失败的任务
4. WHEN 查看死信队列时 THEN 应显示所有失败任务并支持重新处理
5. WHEN 监控系统时 THEN 应提供API接口查询队列统计信息
6. WHEN 系统异常时 THEN 应集成Bull Board提供Web UI管理界面

### Requirement 7: 服务集成和部署

**User Story:** 作为DevOps工程师，我需要将消息队列服务集成到现有系统中，以便在开发和生产环境中稳定运行。

#### Acceptance Criteria

1. WHEN 部署消息队列服务时 THEN 应更新docker-compose.yml添加Redis和消息队列服务
2. WHEN 配置Redis时 THEN 应支持持久化配置以防止数据丢失
3. WHEN 其他服务需要使用消息队列时 THEN 应提供统一的客户端SDK
4. WHEN 服务启动时 THEN 应自动连接到消息队列服务
5. WHEN 服务停止时 THEN 应优雅关闭，确保正在处理的任务完成
6. WHEN 部署到生产环境时 THEN 应使用云服务商的托管Redis服务（如AWS ElastiCache）

### Requirement 8: 数据一致性保障

**User Story:** 作为系统架构师，我需要确保使用消息队列后系统的数据一致性，以便保证业务数据的准确性。

#### Acceptance Criteria

1. WHEN 发布事件时 THEN 应在数据库事务提交后再发送消息（Outbox模式）
2. WHEN 处理消息时 THEN 应实现幂等性处理，避免重复消费
3. WHEN 跨服务操作时 THEN 应使用Saga模式处理分布式事务
4. WHEN 消息处理失败时 THEN 应支持补偿操作回滚业务状态
5. WHEN 系统恢复时 THEN 应能够从中断点继续处理未完成的任务

## 非功能性需求

### 性能要求
- 消息处理延迟应小于100ms（P95）
- 支持每秒处理至少1000条消息
- 队列积压不应超过10000条消息

### 可靠性要求
- 消息不丢失率应达到99.99%
- 系统可用性应达到99.9%
- 支持消息持久化

### 可扩展性要求
- 支持水平扩展消息处理器
- 支持动态添加新的队列类型
- 支持多实例部署

## 约束条件

1. 必须与现有NestJS技术栈兼容
2. 必须支持TypeScript类型安全
3. 部署复杂度应尽可能低
4. 学习曲线应适合团队当前技术水平
5. 应优先考虑开源方案，降低成本

## 成功标准

1. 完成技术选型文档并获得团队认可
2. 成功部署消息队列服务并通过集成测试
3. 至少完成3个核心业务流程的异步化改造
4. 系统响应时间提升30%以上
5. 服务间耦合度降低，单个服务故障不影响其他服务
6. 提供完整的监控和管理能力
