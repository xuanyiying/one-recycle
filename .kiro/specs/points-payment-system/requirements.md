# Requirements Document

## Introduction

本需求文档定义了OneRecycle平台的积分支付系统。该系统将改变当前的支付流程，用户完成回收订单后不再直接收到现金支付，而是获得积分记录到账户余额中。用户可以随时申请提现，将积分转换为真实货币。这种模式可以提高用户粘性，降低即时支付成本，并为平台提供更好的现金流管理。

## Requirements

### Requirement 1: 用户积分账户管理

**User Story:** 作为一个回收用户，我希望拥有一个积分账户来记录我的回收收益，以便我可以查看余额并管理我的资金。

#### Acceptance Criteria

1. WHEN 用户首次登录系统 THEN 系统应自动为该用户创建一个积分账户，初始余额为0
2. WHEN 用户查询账户信息 THEN 系统应返回当前可用余额、冻结余额和总余额
3. WHEN 用户查询账户历史 THEN 系统应返回所有交易记录，包括类型、金额、时间、订单号和余额变化
4. IF 用户账户不存在 THEN 系统应在首次交易时自动创建账户
5. WHEN 用户在小程序中查看个人中心 THEN 应显示当前积分余额和提现入口

### Requirement 2: 订单完成后积分入账

**User Story:** 作为一个回收用户，当我的回收订单完成后，我希望自动获得相应的积分，以便我可以累积收益。

#### Acceptance Criteria

1. WHEN 回收订单状态变更为"已完成"(COMPLETED) THEN 系统应自动计算订单结算金额并增加用户积分
2. WHEN 积分入账成功 THEN 系统应创建一条交易记录，类型为"ORDER_INCOME"，包含订单号和金额
3. WHEN 积分入账失败 THEN 系统应记录错误日志并支持重试机制
4. IF 同一订单已经入账 THEN 系统应拒绝重复入账并返回错误信息
5. WHEN 积分入账成功 THEN 系统应发送通知给用户，告知入账金额和当前余额
6. WHEN 订单被取消或退款 THEN 系统应从用户账户扣除相应积分（如果已入账）

### Requirement 3: 用户提现申请

**User Story:** 作为一个回收用户，我希望能够申请将我的积分提现到真实账户，以便我可以使用这些收益。

#### Acceptance Criteria

1. WHEN 用户发起提现申请 THEN 系统应验证用户可用余额是否足够
2. WHEN 用户提现金额小于最低提现额度(10元) THEN 系统应拒绝申请并提示最低提现额度
3. WHEN 用户提现金额大于可用余额 THEN 系统应拒绝申请并提示余额不足
4. WHEN 提现申请创建成功 THEN 系统应冻结相应金额，创建提现记录，状态为"PENDING"
5. WHEN 提现申请创建成功 THEN 系统应创建一条交易记录，类型为"WITHDRAWAL_FREEZE"
6. IF 用户有正在处理中的提现申请 THEN 系统应允许创建新的提现申请（不限制并发提现）
7. WHEN 用户查询提现记录 THEN 系统应返回所有提现申请，包括状态、金额、时间和处理结果

### Requirement 4: 提现处理和真实支付

**User Story:** 作为系统管理员，我需要处理用户的提现申请并调用真实支付接口，以便用户能够收到真实货币。

#### Acceptance Criteria

1. WHEN 管理员审核通过提现申请 THEN 系统应调用真实支付接口（微信或支付宝）进行转账
2. WHEN 支付接口调用成功 THEN 系统应更新提现状态为"SUCCESS"，扣除冻结金额，创建"WITHDRAWAL_SUCCESS"交易记录
3. WHEN 支付接口调用失败 THEN 系统应更新提现状态为"FAILED"，解冻金额，创建"WITHDRAWAL_FAILED"交易记录
4. WHEN 管理员拒绝提现申请 THEN 系统应更新提现状态为"REJECTED"，解冻金额，创建"WITHDRAWAL_REJECTED"交易记录
5. IF 提现处理超时(24小时) THEN 系统应自动解冻金额并更新状态为"TIMEOUT"
6. WHEN 支付接口返回异步通知 THEN 系统应更新提现状态和交易记录
7. WHEN 提现成功 THEN 系统应发送通知给用户，告知提现成功和到账金额

### Requirement 5: 交易记录和审计

**User Story:** 作为系统管理员和用户，我需要查看完整的交易记录，以便进行财务审计和问题追踪。

#### Acceptance Criteria

1. WHEN 发生任何账户余额变动 THEN 系统应创建一条交易记录，包含类型、金额、时间、关联订单/提现ID
2. WHEN 用户查询交易记录 THEN 系统应支持按时间范围、交易类型筛选
3. WHEN 管理员查询交易记录 THEN 系统应支持按用户ID、交易类型、时间范围筛选
4. WHEN 查询交易记录 THEN 系统应返回分页结果，每页最多50条
5. WHEN 交易记录创建 THEN 系统应记录交易前余额和交易后余额，确保可追溯性
6. IF 发现账户余额异常 THEN 管理员应能够通过交易记录追溯所有变动

### Requirement 6: 小程序界面集成

**User Story:** 作为回收用户，我希望在小程序中方便地查看积分和申请提现，以便我可以轻松管理我的收益。

#### Acceptance Criteria

1. WHEN 用户打开个人中心页面 THEN 应显示当前积分余额、冻结余额和可提现金额
2. WHEN 用户点击"提现"按钮 THEN 应跳转到提现申请页面
3. WHEN 用户在提现页面输入金额 THEN 应实时验证金额是否符合要求（最低10元，不超过可用余额）
4. WHEN 用户提交提现申请 THEN 应显示加载状态，成功后跳转到提现记录页面
5. WHEN 用户查看提现记录 THEN 应显示所有提现申请，包括状态、金额、申请时间
6. WHEN 用户查看交易明细 THEN 应显示所有收入和支出记录，包括订单收入和提现记录
7. WHEN 订单完成后 THEN 应在订单详情页显示"已入账"状态和入账金额

### Requirement 7: 安全性和并发控制

**User Story:** 作为系统架构师，我需要确保积分系统的安全性和数据一致性，以防止资金损失和欺诈行为。

#### Acceptance Criteria

1. WHEN 执行账户余额变动操作 THEN 系统应使用数据库事务确保原子性
2. WHEN 并发处理同一账户的多个交易 THEN 系统应使用乐观锁或悲观锁防止余额不一致
3. WHEN 用户提现申请创建 THEN 系统应验证用户身份和账户所有权
4. WHEN 调用支付接口 THEN 系统应使用幂等性机制防止重复支付
5. IF 检测到异常交易模式（如短时间内大量提现） THEN 系统应触发风控警报
6. WHEN 处理支付回调 THEN 系统应验证回调签名和来源合法性
7. WHEN 记录敏感操作 THEN 系统应记录操作日志，包括操作人、时间、IP地址

### Requirement 8: 消息队列集成

**User Story:** 作为系统架构师，我需要使用消息队列处理异步任务，以提高系统性能和可靠性。

#### Acceptance Criteria

1. WHEN 订单状态变更为"已完成" THEN 系统应发布消息到消息队列，触发积分入账
2. WHEN 提现申请创建成功 THEN 系统应发布消息到消息队列，触发通知发送
3. WHEN 提现处理完成 THEN 系统应发布消息到消息队列，触发通知发送
4. IF 消息处理失败 THEN 系统应支持自动重试机制（最多3次）
5. WHEN 消息重试失败 THEN 系统应将消息移入死信队列并记录错误日志
6. WHEN 积分入账失败 THEN 系统应支持手动重试或补偿机制
